## 一、测试目标

MVP 只认「基本」档，所以测试只回答四个问题：

1. **数值对不对**：BMR / TDEE / 能量目标 / 三餐分配 / 双口径热量，是否与需求公式一致、是否可复现。
2. **该拦的拦没拦**：过敏、慢病、禁忌是硬约束，漏一道就是安全问题。
3. **话有没有说过头**：不编数值、不做诊断、口径不混、来源可查。
4. **能不能交付**：性能指标达标、异常不崩、无越权。

「有条件」档（反向营养、周食谱、历史记录、环境修正、原理讲解）按 **P1** 测：能跑通就算过，跑不通记缺陷但不阻断 MVP 验收。

- 营养学正确性的专业评审（数值与《中国食物成分表》的一致性抽查即可，专业结论由营养专业方背书）。

## 三、策略

| 层次 | 做法 | 是否需要环境 |
|---|---|---|
| L1 数值口径 | 用权威公式独立手算基准值，与系统输出逐项比对（容差 ±2%） | 否（已离线完成） |
| L2 工具契约 | 打桩后端，校验 12 个工具的 URL / 方法 / 入参 / 错误降级 | 否（已离线完成） |
| L3 指令覆盖 | 把 FR 条款拆成关键词矩阵，检查系统指令是否真的约束了模型行为 | 否（已离线完成） |
| L4 端到端 | CLI / Web 真实对话，按 R-01~R-10 场景跑 | 需后端 + LLM key |
| L5 性能 | 脚本压测，取 P95 / P99 | 需部署环境 |
| L6 安全 | 越权访问、字段加密抽查 | 需后端 + DB 权限 |

**判定口径**：需求里写死的数值（1340 kcal、30/40/30、1g 油=9 kcal）按硬断言；需求只给区间的（供能比 50~65%）按区间判定；措辞类要求（"可能/建议关注"）按关键词 + 人工判读。

## 四、环境（当前实测状态）

| 项 | 状态 | 影响 |
|---|---|---|
| 被测代码 | ✅ 已就位 `E:\RG\agent_1` | — |
| 后端服务 | ❌ **不在本机**。8000/8080/9000/3000 均无监听，直连 `000`；`E:\RG` 下只有 Agent 层，无后端源码 | 所有 L4 用例 BLOCKED |
| 后端地址 | ❌ **未知**，交付包内无任何服务器地址记录，也没有 `.env` | 无法配置 `BACKEND_BASE_URL` |
| `DEEPSEEK_API_KEY` | ❌ 无 `.env`，仅有 `.env.example` 模板 | 无法起 Agent |
| `agno` 依赖 | ❌ 未安装（`requirements.txt` 声明 `agno==2.8.7`） | 无法直接 `python main.py` |
| 前端 | ❌ 未提供 | TC-UI / TC-CP 全 BLOCKED |

> 结论：**当前不具备端到端验收条件**。已把不依赖环境的 L1~L3 全部跑完，端到端部分按计划挂起等环境。

**恢复测试需要组里提供 4 样东西**（按重要性）：

1. 后端服务地址（`http://<ip>:8000`，且 `/api/health` 可达）—— 最关键。
2. 一个可用的 `DEEPSEEK_API_KEY`（或说明统一由谁的 key 承担调用成本）。
3. 前端访问地址（Web 版）。
4. 数据库只读账号（仅用于 FR-03 字段加密抽查、TC-SC-01）。

拿到后在 `E:\RG\agent_1\.env` 写：

```
DEEPSEEK_API_KEY=sk-xxxx
DEEPSEEK_MODEL=deepseek-v4-flash
BACKEND_BASE_URL=http://<后端IP>:8000
```

**准入**：后端 `/api/health` 返回 200；`.env` 配好 key；`pip install -r requirements.txt` 无冲突。

- R-01~R-10 十条验收任务全部通过；

**不满足则**：P1 缺陷全部修复并回归；P2 缺陷列已知问题随交付说明，不阻断。

## 七、风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 后端迟迟拿不到地址 | 端到端无法验收，只能交离线报告 | 先把离线部分做扎实；尽早向组里要地址 |
| LLM 输出不稳定，同一输入两次结果不同 | 功能用例难以判定 PASS/FAIL | 数值一律以工具返回为准判定；措辞类用例每场景跑 3 次取多数 |
| 菜品库/食材库数据不全 | 会误判为"配餐逻辑 bug" | 缺数据记「数据缺陷」并转数据岗，不计入 Agent 缺陷 |
| 无营养专业方背书 | 数值"对"但营养学"不合理" | 数值一致性抽查为止，专业结论留白 |
| 需求本身有矛盾（如 BUG-05 的 1920 vs 1482） | 测出来的"bug"其实是文档问题 | 先实测定位根因，再决定是改代码还是改文档 |
