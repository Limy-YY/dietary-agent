> 目的：给「已确诊疾病 → 候选硬过滤」定口径，作为 BUG-035 的接线依据。
> 日期：2026-11-23。

> **进展（2026-11-23）**：§四映射表里的「痛风 → `purine_level=高` L0 硬排除」已落地——`repository._DISH_SQL` 把 `core.ingredient.purine_level` 按「最高已知等级」聚合到 `DishFacts.purine_level`，`candidates.CONDITION_HARD_FILTER` 对 `confirmed_conditions` 含 `gout` 且菜为「高」时硬排除；其余病种（高血脂/糖尿病/高血压）仍待 §五 D0 词表与 D1–D4 拍板后再接。**数据口径提醒**：现库「高」嘌呤食材含 `鸡胸肉`（生成池 15 道高嘌呤菜中 8 道由鸡胸肉驱动），若数据岗认为鸡胸肉应归「较高」，请下调后重新灌库，L0 排除量会随之下降。

## 一、问题

8 条共享铁律①「过敏 / 疾病 / 宗教 = 硬排除」里，**过敏、宗教已接硬过滤，唯独「疾病」只有提示**：

- `targets.py` 只把 `confirmed_conditions` 写进 `condition_note`（一句文案），`candidates.py:hard_filter_reasons` 从不引用它。
- 数据侧 `42_疾病规则口径审核_v1.2r4.sql` 已落 9 条规则、7 条生效，但其中 6 条是 `pattern_preference` / `review_gate`（`numeric_evaluation=false`），**只有高血压钠 1 条是可判定的数值规则**，且它已由「盐上限 + BUG-050 总钠软扣分」覆盖。
- 结论：**不是「忘了接」，而是「没有量化的疾病→食材/营养素排除映射可接」**。硬接会凭不完整数据误排除食材，违背 null≠0 与 data_quality 三态。

本提案把「疾病硬过滤」拆成**按数据成熟度分级**落地，并明确哪些可直接做、哪些要数据岗补字段、哪些要 PM 拍板。

### 2.2 食材侧可用的「硬过滤信号」字段（`core.ingredient`）

| 字段 | 类型 | 用途 | 数据完整度 |
|---|---|---|---|
| `purine_level` | text（低/中/高/NULL） | 痛风：高=硬排除、中=软限 | ✅ 已随食物成分表补录（NULL 表未知） |
| `sfa_g` | numeric | 高血脂：饱和脂肪酸软限 | ✅ 有值 |
| `cholesterol_mg` | numeric | 高血脂：胆固醇软限 | ✅ 有值 |
| `sodium_mg` | numeric | 高血压：钠（已覆盖） | ✅ 有值 |
| `category` | text | 按食材类别做 pattern 偏好 | ✅ 有值（但取值域未与规则 selector 对齐） |
| `tags` | text[] | 补充分类/关键词 | 部分 |

### 2.3 做法侧信号

- `core.cooking_rule.added_sugar_level`（text）——糖尿病「高添加糖闸门」可据此把高糖做法菜排除/复核。

### 2.4 明确缺口（导致无法做「数值级」过滤）

- `core.nutrient` 无 `carbohydrate / added_sugar / saturated_fat / purine` 字典；`app.nutrition_result.computed` 无 `sugar_g / carb_g / purine_mg / sfa_g` 聚合。
- `core.ingredient` 无 `gi_value`（升糖指数），低 GI 只能靠「全谷物/杂豆」这类类别代理。
- 规则 selector 的 `prefer_categories / review_categories` 是**人类可读的食物大类**（如「全谷物」「甜点与含糖饮料」「部分海鲜」），与 `core.ingredient.category` 的实际取值域**没有映射表**——这是接线前必须先补的一张词表（类比过敏原的 `ALLERGEN_ALIASES`）。

## 三、核心口径：三层分级

| 层级 | 语义 | 落地方式 | 触发条件 |
|---|---|---|---|
| **L0 硬排除** | 确定性「不进方案」 | `hard_filter_reasons` 直接排除 | 数据完备、语义无歧义（=过敏/宗教同款） |
| **L1 强软约束** | 尽量避、超阈值显著降权/末位 | `_score` 加分 + reason_code + 提示 | 数据有信号但不宜硬排（天然食物中含某种成分 ≠ 禁忌） |
| **L2 复核闸门** | 默认不排，确需时追问用户确认 | Agent 追问 / review_gate | 无量化字段，只能按「类别/等级」粗判 |

**关键原则**：只有「能证明『某食材对某病种是明确禁忌』」才上 L0 硬排除。其余一律 L1/L2，避免把「全谷物」「鱼类」这种健康食材误杀。

## 五、待拍板决策点（请 PM / 数据岗定）

- **D1｜痛风是否上 L0 硬排除？** 推荐「是」——`purine_level=高` 的食材（动物内脏、浓汤、部分海鲜）对痛风是明确禁忌，且数据已就绪，硬排最安全。若保守，可先 L1、待急性期场景再加 L0。
- **D2｜高血脂/糖尿病的「类别降权」按什么强度？** 推荐 L1（强软、超阈值末位 + 提示），不做 L0——「肥肉」对高血脂是应避免、但不至于像过敏一样绝不可碰。
- **D3｜冲突求解（P3）**：疾病硬排除 vs 用户点名（如痛风患者点名「猪肝」）——推荐：**硬排除优先**，Agent 明确告知「因你确诊痛风，这道高嘌呤菜已排除」，不做静默替换。与过敏/宗教同口径。
- **D4｜review_gate 在对话里怎么表达？** 推荐：默认不排 + 一句话告知「已避开高糖/高嘌呤菜品」；用户追问「就想吃 X」时再走「确认份量/风险提示」追问，不主动诱导。

## 六、推荐落地顺序

### Phase 1（可立即做，后端 P1，数据零改动）
1. **D0 词表**：数据岗补一张「规则食物大类 → `ingredient.category`/`tags`/名称关键词」映射（可先只覆盖痛风/高血脂/糖尿病三病种 selector 里出现的大类，共 ~15 类），落到 `core` 字典或后端常量（类比 `ALLERGEN_ALIASES`）。
2. **后端**：`repository.get_dish_facts` 的 `DishFacts` 透出 `purine_level`（食材级聚合：一道菜含任一「高」→高）与 `sfa_g`/`cholesterol_mg` 聚合；`hard_filter_reasons` 增加「疾病硬排除」分支（只做痛风 L0）；`_score` 增加高血脂/糖尿病/高血压的 L1 软扣分。
3. **Agent**：`_INTENT_SYSTEM` 与生成分支把 `confirmed_conditions` 纳入叙事素材，生成时如实说明「已按你确诊的 X 避开 Y」。

### Phase 2（需数据岗补字段/口径）
4. `core.ingredient` 补 `gi_value`（或 `glycemic_category`），糖尿病才能从「类别代理」升级为「低 GI 优先」。
5. `cooking_rule.added_sugar_level` 接线糖尿病 L2 闸门。

### Phase 3（数值级，课程后）
6. 补 `core.nutrient` 的 `added_sugar / saturated_fat / purine` 字典 + `nutrition_result.computed` 聚合，才谈得上「日摄入数值达标判定」（对应 CLAUDE.md P1/P4）。

---

## 七、结论（一句话）

**先把「痛风 → 高嘌呤食材」接成 L0 硬排除（数据已就绪、语义无歧义），其余病种按 L1 软约束 / L2 闸门落地；数值级疾病判定等 Phase 3 补齐字典与聚合后再做。** 在数据岗给出 §五 D0 词表与 D1–D4 拍板前，不擅自把「疾病」当硬排除写进候选过滤。
