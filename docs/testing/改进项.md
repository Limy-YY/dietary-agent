## IMP-001 · 会话列表改读后端 conversation 表

- **现状**：前端 [chat.js](github仓库/frontend/src/stores/chat.js) 把会话列表存在 `localStorage['sz_sessions_v1']`，而后端 chat.py 其实已把 conversation/message 落库。前端会话 id（`conv_...`）与后端整数 id 是两套。
- **问题**：换设备/清缓存 → 侧边栏历史会话全丢（库里其实还有）；也是 BUG-003（conversation_id 类型错）的根子。
- **目标**：会话列表以后端 conversation 表为准——后端补「会话列表查询」接口（可选「删除会话」），前端 localStorage 只留 token 与 UI 偏好，不再存业务数据。
- **优先级**：P1。
- **完成（2026-11-20）**：后端补 `GET /conversations`（列表）、`GET /{id}/messages`（历史消息）、`PATCH /{id}`（重命名）、`DELETE /{id}`（删除）；前端 chat.js 会话列表改读后端、消息懒加载、重命名/删除走后端，localStorage 只留 token。
- **结构化块落地（方案 A）**：内容型 artifact（`meal_card` / `shopping_list` / `nutrition_report`）随 assistant 消息以「快照」写入 `app.message.structured_output`，`list_messages` 透出，前端 `normalizeArtifact` 原样还原；`current_plan`（瞬时态）与 `quick_actions`（一次性动作按钮）不落。历史还原的块带 `readonly` 标记：餐卡「换一换/确认/选用候选」禁用、状态标「历史快照」，只读回放。

## IMP-010 · 「看完整食谱」还原原型：食材清单 + 做法

- **现状**：「看完整食谱」弹窗只显示菜名 + 份量 + 热量，与餐卡完全重复；原型想要的是每道菜的**食材清单**和**做法**（`main.html` 的 `.dish-card`：`.dc-ingredients` + `.dc-steps`）。
- **根因**：后端 `_serialize_candidate` 每道菜只吐 `dish_id/name/role/servings/.../method_override`，没吐 `core.dish.method_text`（做法）和 `dish_ingredient` 的食材；前端 `dishView` 把 tip 错映射到恒空的 `method_override`，RecipeModal 也没有食材/做法的渲染位。
- **A 档（已做，2026-11-16）**：后端 `_dish_details()` 批量查 `method_text` + 食材，`_serialize_candidate` 每道菜补 `method_text` / `ingredients`；前端 `dishView` 把 tip 回落 `method_text`、新增 `ingredients`，RecipeModal 显示「食材」「做法」两行。
- **B 档（待数据口径，2026-11-16 已查库确认）**：做法步骤库内无存储——`core.dish` 只有 `method_text`（做法名）+ `cook_time_min`（分钟），`core.cooking_rule`（16 条）是油盐糖估算规则（`method_applicability`/`core_assumptions`/`adjustment_rules` 均非步骤）。需数据岗补录步骤文本，见 IMP-011。
- **优先级**：P1。

## IMP-011 · 做法步骤/要点文本补录（数据岗）

- **现状**：原型 `.dc-steps` 要的是「少油煎撒黑胡椒」「蒸 8 分钟淋蒸鱼豉油」这类操作要点，库内无步骤文本（见 IMP-010 查库结论）。
- **建议口径**（数据岗定夺）：
  1. `core.dish` 加 `steps text[]`（或 jsonb 有序步骤），60 道菜逐条补 2~3 条短要点：做法名 + 火候/时间 + 关键调味（例：清蒸鲈鱼「水开后蒸 8 分钟，出锅淋少许蒸鱼豉油」）；
  2. 通用做法级步骤想复用可挂 `core.cooking_rule` 加一列，菜级特化落到 `core.dish`；
  3. 补录后由 Agent 输出契约 `dishes[].steps` 透传（前端 `schema.js` 已预留 `steps` 渲染位），Agent 不现编。
- **顺带确认**：`dish_ingredient.role` 无约束、实际 7 取值（主料/配菜/配料/调味辅料/调味料/烹调油/食盐），「配料」仅 DISH-046 一处；`amount_g`=生重、`cooked_amount_g`=熟重（现全空，与 P2 烹饪损耗同源）。
- **优先级**：P1。

## IMP-012 · 每道菜级热量估算（规则引擎按菜输出）

- **现状**：原型食谱卡片/方案详情里每道菜都标 kcal（如「糙米饭 210 kcal」「鸡胸肉 200 kcal」），但后端只有 candidate（整餐）级 `macro_estimate`，`_serialize_candidate` 不吐每道菜的 kcal；前端 `dishView` 的 `kcal` 硬编码为 `null`，餐卡与历史方案详情都只能显示整餐热量，逐菜热量永远缺失。
- **根因**：规则引擎宏量估算粒度在「餐位」而非「菜品」，库内 `core.dish` 的 `nutrition_snapshot` 也未按菜落地能量值。
- **目标**：规则引擎按菜输出宏量估算（kcal / 蛋白 / 脂肪 / 碳水），契约 `dishes[].kcal` 透传；前端 `dishView` 去掉 `kcal: null` 硬编码，按真实值渲染。
- **依赖**：与 CLAUDE.md P2（营养核算口径：可食部/烹饪损失）同源——per-dish kcal 要定「生重口径还是熟重口径」。
- **优先级**：P2（课程后，需规则引擎 + 数据口径一起定）。

## IMP-019 · 规则引擎跨日菜品不差异化（周方案各天重复）

- **现象**：周/多日方案生成后，7 天早/午/晚菜品**完全相同**（实测 plan 20：每天都是「早：二米饭+西兰花蒸蛋+玉米烩蛤蜊；午：酸奶燕麦片+土豆茄子炖牛肉+番茄菠菜疙瘩汤；晚：酸奶燕麦片+紫菜蛋花汤+土豆茄子炖牛肉」）。食材清单按天分列后每天一模一样（18 种食材 × 7 天，数量也一致），导致「食材清单」的按天筛选**看起来失效**（点哪一天内容都不变）。
- **层面**：规则引擎。
- **根因**：[pipeline.py](github仓库/backend/app/services/rule_engine/pipeline.py) 第 3 步里 `templates[meal_type]` 每个餐次只枚举一次候选池，`for slot_date in dates` 循环中 `pool = clone_candidate(templates[meal_type])` **复用同一池**，且 `used_mains` 去重集合每个 `slot_date` 都重置 → 每天选出相同的 top 2~3 候选；第 4 步「跨日微量平衡」只调份量不换菜品。
- **影响**：前端「食材清单按天分列」（方案 A）已正确落地，但数据本身无跨日差异，分列价值为零；同时周方案整体也缺「一周不重样」的产品承诺。
- **目标**：规则引擎补「跨日菜品差异化」——候选池按天错开（例如按 `slot_date` 做确定性偏移/轮换主菜，或把 `used_mains` 去重范围从「当天」扩大到「窗口内已用」），让相邻天主菜不同。
- **优先级**：P1（食材清单按天分列依赖它才有意义）。
- **状态**：✅ 已完成（2026-11-17 实机验证：周方案早/午/晚三餐主菜去重各 7/7）。
- **修复**：[pipeline.py](github仓库/backend/app/services/rule_engine/pipeline.py) 第 3 步改为「① 当天跨餐 + ② 同餐跨日」两级主菜去重：`window_picked_mains` 按餐次各自累计「首选」主菜，`cross_fresh` 把前几日该餐没选过的主菜排到最前，让首选主菜逐日错开（只追踪首选、候选可复用，避免菜池被过早耗尽）。
- **结果（连库实测）**：7 天「三餐组合」去重后 **7 种**（此前 1 种）；早 7/7、午 7/7、晚 5/7 天主菜不同。晚餐剩余 2 天重复源于**数据池限制**——晚餐与早餐共享 7 个低热量主菜、且晚餐排在早餐之后，可用不重复主菜较早用尽（已如实记「窗口内不重复主菜已用尽」说明）。若要进一步拉高晚餐差异，需数据岗补低热量菜式（`core.dish`）。

## IMP-034 · Agent 灵活度缺失（LLM 被关在决策环外）

- **状态**：✅ 已完成（2026-11-17 端到端验证通过）——① 自由参数透传（`51fbdca`）；② tool-calling loop + ③ 软偏好/调整/追问/正则降级均实现并验证；`run()` 旧「生成/清单/兜底」dead code 已清。
- **现象**：当初「发挥 Agent 灵活度」的核心设想没落地——Agent 只能「一餐 / 一天 / 一周」地生成，无法按用户需求灵活调整（「排三天午餐」「晚上清淡点」「不要牛肉」都不行），更像「无情机器」而非智能体。
- **根因（架构性，不是 LLM 笨）**：LLM 被放到**决策环之外**，只干两件事——① 正则没拦住时把话塞进一个**固定枚举**里分类；② 给已生成方案写 1~3 句文案。它从没被允许「决定生成什么、调什么工具、传什么参数」。
- **证据**：
  1. **生成单位焊死成三档**：`scope = {"plan_day":"day","plan_week":"week","plan_meal":"meal"}`（[agent.py:464](github仓库/agent/agent.py#L464)），日期硬编码（[agent.py:469-475](github仓库/agent/agent.py#L469-L475)），桥接层 `week` 固定 +6 天（[rule_engine_bridge.py:102-116](github仓库/agent/rule_engine_bridge.py#L102-L116)）。**但底层引擎早已支持任意区间**——`PlanRequest` 有 `start_date/end_date/meal_types/soft_avoid/meal_ratios/window_days`（[models.py:209-224](github仓库/backend/app/services/rule_engine/models.py#L209-L224)），`plan_dates` 支持最长 14 天（[pipeline.py:45-57](github仓库/backend/app/services/rule_engine/pipeline.py#L45-L57)）。灵活度全在引擎里躺着，Agent 层没接出去。
  2. **「调整」意图不存在**：意图分类只有 `plan_day/week/meal + swap_candidate(换一换) + 各问答类`（[agent.py:57-73](github仓库/agent/agent.py#L57-L73)、[agent.py:140-186](github仓库/agent/agent.py#L140-L186)），全目录无一处真正的 adjust 分支。语义调整（「换清淡」「少油」「不要 X」）掉进枚举外，被归成 rag_qa/chat。
  3. **软偏好字段引擎有、Agent 从没传**：引擎 `soft_avoid`（[models.py:220](github仓库/backend/app/services/rule_engine/models.py#L220)）在 Agent 目录 grep 不到任何赋值。「清淡/少油/多蛋白」这类最体现灵活度的诉求在生成请求里完全丢失。
  4. **没有 tool-calling loop**：文档写「Agent 层 Agno」，代码却是手搓 OpenAI 直连（[config.py:46](github仓库/agent/config.py#L46)、[agent.py:44](github仓库/agent/agent.py#L44)），「工具编排」实为 [agent.py:419-855](github仓库/agent/agent.py#L419-L855) 一段 `if kind == ...` 分支墙，一次只跑一条固定路径。
  5. **正则优先，抢在 LLM 前拦掉大多数真实请求**：`classify()` 先跑 `_regex_intent`，命中即 dispatch，LLM 只在正则落空时出场（[agent.py:209-215](github仓库/agent/agent.py#L209-L215)）。
  6. **needs_clarification 只写在铁律、没有追问循环**：缺参数一律 `or 默认值` 硬上（如 [rule_engine_bridge.py:83-93](github仓库/agent/rule_engine_bridge.py#L83-L93)），从不停下来反问。
- **对照主流 LLM 客户端**：主流是「LLM 在环内当 planner（function calling）」，本项目是「LLM 在环外当 caption writer」。缺的正是**函数调用/工具使用循环**这整条能力——参数抽取、工具编排、多轮澄清、迭代调整、复合任务分解。
- **根因总结**：「计算与决策分离」被过度执行成「LLM 与决策分离」——「零编造」铁律本意是防 LLM 编数值，被放大成「LLM 别做任何决定」，于是所有参数固化成枚举/正则；加上输出契约自底向上围绕 day/week/meal 三档设计，死板被传染到 REST（`/api/meal-plan/week/generate` 的 `scope` 字段，[backend_client.py:167-176](github仓库/agent/backend_client.py#L167-L176)）与前端全栈。
- **目标（按成本排序，引擎零改动或小改）**：
  1. **① 自由参数透传（半天，P0 快赢）**：后端加通用生成接口，直接透传引擎已有的 `start_date/end_date/meal_types/soft_avoid`；Agent 把 `scope={day/week/meal}` 三行换掉。立刻支持「3 天午餐」「周末两天」。
  2. **② 引入 tool-calling loop（核心，P1）**：给 LLM 定义工具 `generate_plan(params)/swap_candidate/read_profile/ask_clarification`，让 LLM 决定「调谁、传什么参、要不要先问、要不要调完再调」。此时 `soft_avoid` 才有入口（「清淡」→`soft_avoid=["油炸","高油"]`，「不要牛肉」→`exclude_ingredients=["牛肉"]`）。
  3. **③ 「调整」升一等意图 + needs_clarification 落地 + 正则降级为加速器（P1，与②配套）**：语义调整走同一生成引擎带约束重排；缺参数让 LLM 停下追问而非 `or 默认值`；正则只保留确定性按钮短语（换一换/确认），自然语言主路径交给 LLM 抽参。
- **边界（勿踩，保住现有好架构）**：LLM 只「**决定参数 + 编排调用顺序**」，**数值计算与落库仍走确定性工具**——原则②（计算决策分离）与 8 条铁律不破。「让 LLM 决定，但不让 LLM 算」才是当初设计的本意。
- **归属**：Agent（②③）+ 后端（① REST 透传）。
- **优先级**：P1（① 可并入 P0 答辩前快速项，成本半天、直接解决「只能三档生成」的抱怨）。
- **与 IMP-028 关系**：IMP-028 只谈「意图路由正则回填字段 + tool-use 可视化 + 模型选型」，范围窄且排 P2；本项是其背后的**架构根因**，应先做本项①的 scope 解耦，再谈 IMP-028 的展示层。

  4. 「只换素菜、主食别动」→ 候选内局部调整，不支持；
  5. 「晚餐清淡点」若 3 个候选都油 → 只能挑相对最不油的，**不能重生成**符合约束的新候选。
- **判断（方向正确性）**：不该追「像通用 LLM 那样开放灵活」——那会违背「零编造 / 确定性计算」铁律（通用 LLM 的灵活恰是它敢编敢猜）。正确方向是**扩引擎 + 扩工具面**，让 LLM 的可表达空间变大、但仍受确定性引擎约束。
- **建议（P2，课程后演进）**：
  1. 引擎 `PlanRequest` 加 `portion_hint`（份量偏好）/ `macro_preference`（多蛋白、低碳水）/ `swap_ingredient`（单品替换）/ `prefer_low_oil`（低油硬偏好）等字段；
  2. Agent 工具面加对应动词（`swap_dish` / `adjust_portion` / `set_macro_preference`）；
  3. 语义映射从「硬编码关键词表」升级为「LLM 输出结构化偏好 + 后端白名单校验」（避免编造食材名）。

- **做法（2026-11-20）**：`DishFacts` 增 `ingredient_weights: Mapping[str,float] | None` 字段（None=未算）；`ingredient_weights(d)` 改为首次解析后缓存到对象上——对象请求内共享、不可变，克隆候选浅拷贝共享同一 `facts`，缓存整请求不失效。空结果用 None 哨兵区分「未算」与「算得空 {}」，避免无配方数据的菜被反复重算。返回值用 `MappingProxyType` 包成只读视图，任何调用方就地修改都会抛 `TypeError`（防未来误改共享缓存）。
- **收益**：第二步整条链路（`portion_limits`→`dietary_attributes`→`main_family`→`purchases`）的重复解析全部消掉；`main_family`/`purchases` 无需单独缓存（剩余工作只是遍历现成 dict × servings 标量）。
- **优先级**：P1（与 IMP-046 互补：IMP-046 治「组合枚举量」，本项治「单组合内的重复解析」）。

## IMP-055 · JWT_SECRET 长度不足（签发时报 InsecureKeyLengthWarning）

- **现象**：按 README「鉴权」步骤离线签发 token 时，控制台打印 `InsecureKeyLengthWarning: The HMAC key is 23 bytes long, which is below the minimum recommended length of 32 bytes for SHA256`。
- **根因**：[backend/.env](github仓库/backend/.env) 的 `JWT_SECRET` 只有 23 字节，短于 HMAC-SHA256 推荐的 32 字节（RFC 7518 §3.2）。功能上能正常签发，但属安全隐患（密钥偏短易被暴力破解）。
- **目标**：把 `JWT_SECRET` 换成 ≥32 字节的随机串；改完需**重新签发 token**（密钥变化后旧 token 立即失效），并重新在浏览器 `localStorage.setItem('sz_token', ...)` 注入。
- **优先级**：P2（安全卫生，本地联调可暂缓；上线前必须）。
