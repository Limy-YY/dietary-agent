## 四、三写落库：谁写、写到哪、怎么验

代码核查结论（`grep INSERT / db.add / commit` 全仓）：写库只发生在 `backend/app/routers/`，
`services/rule_engine/` 内没有 INSERT、`db.add` 或 `commit`，它只计算、不落库；Agent 侧也不直连库，
唯一的档案写是 `bc.upsert_profile` 走 REST 回后端。

**Agent → 后端的鉴权链路（2026-11-16 补齐）**：Agent 内部每一次 REST 调用（读档案、建档、生成方案落库）
都要求 JWT，缺了就是 401，现象是"档案明明存在、对话却回还没有你的档案"，方案也不会生成。
链路做法：后端 `_agent_events()` 把调用方 `Authorization` 的裸 token 放进发往 `/chat` 的请求体 →
Agent `main.py` 收到后调 `backend_client.set_token()` → 之后所有 `_get/_post/_put` 自动带 `Bearer`。
另：Agent 传的 `meal_types` 是英文 `['breakfast','lunch','dinner']`，通信契约口径是 `['早','午','晚']`，
`mealplan.py` 加了 `_normalize_meal_types()` 做别名归一，避免整条生成链路因取值非法失败。

| 写 | 接口 | 代码位置 | 落库表 |
| --- | --- | --- | --- |
| 档案写 | `PUT /api/profile`（`POST /api/profile` 同义） | `routers/profile.py:174` INSERT + `:210` commit | `app.profile` |
| 方案写 | `POST /api/meal-plan/week/generate` | `routers/mealplan.py:315` → `_persist_plan()`（`:220`）：`:229` MealPlan、`:254` db.add、`:265` meal_slot、`:295` meal_candidate_dish、`:358` commit | `app.meal_plan` / `app.meal_slot` / `app.meal_candidate` / `app.meal_candidate_dish` |
| 对话写 | `POST /api/agent/chat`（SSE 流式） | `routers/chat.py:78` INSERT conversation、`:93` `_save_message()` INSERT message（`:199` 用户、`:271` 助手）、`:83` / `:98` commit | `app.conversation` / `app.message` |

### 测试岗判据的三处口径纠正

1. `SELECT count(*) FROM core.dishes` —— 库里的表是 **`core.dish`（单数）**，没有 `dishes`；
   照抄会报 `relation "core.dishes" does not exist`，会被误判成"账号没恢复"。正确写法：
   `SELECT count(*) FROM core.dish;`（60）。`knowledge.knowledge_doc` 43、`app.profile` 5 同理可读。
2. `/api/health` 不是统一信封，返回裸 dict：`{"service":"diet-agent-backend","status":"ok","database":"ok"}`，
   **没有 `code` 字段**；"200 / code=0"里的 200 成立、`code=0` 不成立。判据按 `HTTP 200` + `status=ok`
   + `database=ok` 看（Agent 的 `/health` 才是 `{"code":0,...}`）。
3. "一次真实对话后三处各有新增"要分清档案是不是本次建的：档案已存在的用户，对话只会新增
   方案与对话两处；要一次看齐三处，用新 `user_id` 先 `PUT /api/profile` 再对话。

注意：对话在 Agent 服务不可达时**仍会落库**（会话与消息照写，SSE 回一条"Agent 不可达"提示），
所以"库里有 message"不代表 Agent 链路通了，判定 Agent 链路要看 SSE 正文。
