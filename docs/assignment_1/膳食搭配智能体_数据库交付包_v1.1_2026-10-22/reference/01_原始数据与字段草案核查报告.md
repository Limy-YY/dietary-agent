# 膳食搭配智能体：最新版数据包与字段草案逐表核查报告

> 本报告记录v1.0初次核查结果。食材表在2026-10-22再次更新，碘值和嘌呤等级已经补齐；最新状态见 `05_食材数据更新说明.md`。

核查日期：2026-10-21  
核查对象：`数据表汇总.zip` 与《膳食搭配智能体系统-数据字段草案》v0.1  
目标数据库：PostgreSQL 18.6，数据库 `diet_agent`（当前为空库）

## 1. 结论先行

这份最新版压缩包已经具备一套可用的“种子数据”基础，但**不能把整个压缩包原样直接导入正式业务表**。最稳妥的做法是：原件只读归档 → 暂存层导入 → 自动校验 → 转换为关系表 → 通过质量门禁后再发布到核心表。

本次核查结论如下：

- 可以直接导入 PostgreSQL **暂存层**的文件有：`食物成分表.csv`、`food_id映射表.csv`、`cooking_rules.csv`。这里的“直接”是指先全部按文本列接收，不是绕过校验直接进入正式表。
- 可以作为程序读取源、但需要拆分或扁平化后入库的文件有：`dishes.json`、`rni_reference.json`、`nutrients.json`、`dietary_rules.yaml`、`cooking_rules.json`。
- Markdown 说明文件只能作为数据字典和知识来源，不应当作结构化事实表导入。
- `rni_reference_核查表.xlsx` 与 JSON 的 448 条值完全一致，适合人工核查；正式导入应以 JSON 为主，因为 Excel 展示层丢失了 `menstrual_status`，导致“铁 / 女 / 50–64 岁”出现两条看似重复的数据。
- 压缩包没有 `profile`、`meal_plan`、`nutrition_result`、`weekly_nutrition_report`、`conversation`、`message` 的业务记录；这些表应先建空表，运行时由应用产生数据。
- 压缩包没有可直接入库的 `symptom_nutrient_map`；`nutrients.json` 中的“缺乏表现”是知识文本，不能自动等同为医学因果映射。
- 压缩包没有已经切块并生成向量的 `knowledge_doc`；现有营养素知识可以作为生成知识文档的上游数据。
- 字段草案的总体分层思路正确，但对最新版数据来说，`ingredient`、`rni_reference`、`profile`、`dish` 和 `knowledge_doc` 均需补字段或改变键设计。

### 入库前必须处理的 P0 问题

1. **菜谱过敏原状态快照过期。** 30 道菜的 127 条配料关联均能找到食材，过敏原 token 也一致，但其中 **108 条 `allergen_status`** 仍是旧值，通常显示“未核查”，而最新版食材表已标记为“确认不含”。`avoid.strict_allergens` 当前与食材表重新计算的结果一致，但配料级状态仍会误导程序和人工检查。应从食材表统一重算，不要手工逐条改。
2. **RNI 周度比较量纲错误。** RNI/AI/UL 是每日参考值。说明文件中“周累计 `< value` 即不足”的写法不能直接使用。应比较“日均摄入 vs 每日参考值”，或者把每日参考值乘以有效记录天数；UL 还要单独定义是按日最大值、日均值还是超限天数判断。
3. **规则文件相对路径不可直接解析。** `dietary_rules.yaml` 声明的 `食物成分表.csv/json` 不在 YAML 同目录，而是在兄弟目录 `中式食材成分表/`。如果程序按 YAML 所在目录解析，会找不到文件。菜库的 `food_reference` 也只是展示路径，不是可解析的真实相对路径。
4. **用户画像字段契约不一致。** 禁忌规则按 `user_profile.conditions` 激活，而字段草案的 `profile` 没有 `conditions`，仅有 `taboos TEXT[]`。应增加结构化 `conditions JSONB` 或独立的 `profile_condition` 表。

### 建议在首轮入库前修正的 P1 问题

- 根目录说明仍写 116 条食材，实际为 **128 条**。
- 食材说明写“已删除映射表”，但压缩包仍包含 **32 条** `food_id映射表.csv`。
- 根目录说明提到 `rni_reference_adult.json`，压缩包中没有该文件。
- RNI 说明写 436 行，实际 JSON 和 Excel 都是 **448 行**；还写有平铺 CSV，但包内只有 XLSX。
- 禁忌规则说明的过敏状态分布写成 38/84/6，实际为 **39/83/6**。
- 菜谱有 12 个汇总值与按配料重算相差 0.1（11 个热量、1 个蛋白质），属于舍入顺序差异；应统一“先逐项四舍五入再求和”或“先求和再四舍五入”。
- ZIP 带有 20 个 AppleDouble 文件和 2 个 `.DS_Store`，且文件名未写 UTF-8 标志，普通 `unzip` 会显示中文乱码。数据库内容不受影响，但交付包应另外生成一个干净副本，不要覆盖原件。

## 2. 核查范围、方法与边界

本次对压缩包中的 18 个真实内容文件逐一解析，并将 20 个 `__MACOSX/._*` 与 2 个 `.DS_Store` 视为 macOS 打包杂项。核查包括：

- CSV/JSON/XLSX/YAML/Markdown 的文件结构、字段、行数、空值、重复值、数值范围和元数据；
- 同一数据集多格式之间的一致性；
- 食材、菜谱、烹饪规则、禁忌规则之间的外键与快照一致性；
- 与字段草案中的 13 张物理表逐表对照；
- 官方来源网址、发布机构及口径的高层核实。

边界说明：本次确认了来源指向中国营养学会、中国疾控营养与健康所、国家卫健委、USDA、NIH 等权威机构，也做了内部逻辑与跨文件校验；**没有逐项重新抄录并复核 128 种食物的全部营养数值，也没有逐项复核 448 个 RNI 数值**。因此可判断“来源路径可信、结构一致”，但不能把这次核查表述成营养学专家对每个数字的二次鉴定。

## 4. 各数据集详细质量检查

### 4.1 食物成分表

#### 结构与覆盖

- 128 行、46 字段；122 条 `CN-*`、6 条 `FDC-*`。
- 16 个分类，数量最多的是蔬菜 46、水果与果汁 14、水产 13、谷物与面食 12。
- 9 类状态，其中“生”83 条、“干制/未烹调”16 条、“熟制”7 条。
- 122 条来源指向中国食物成分查询平台，6 条指向 USDA FoodData Central。
- `food_id` 无重复，`name` 无重复，`source_url` 全部存在。
- 未发现负数营养值、可食部超出 0–100、或 kJ 与 kcal 相差超过 1 kcal 的记录。

#### 空值并非错误，但必须保留 NULL 语义

高风险缺失如下：

| 字段 | 缺失数 / 128 | 解释与影响 |
|---|---:|---|
| `iodine_ug` | 128 | v1.0初次核查时整列空；v1.1已补齐128条 |
| `fiber_g` | 124 | 仅 4 条有值；不能据此评价多数食材的膳食纤维 |
| `vitamin_e_ate` | 124 | 几乎不可用于全库比较 |
| `purine_level` | 104 | v1.0初次核查时缺失104条；v1.1已全部补齐 |
| `sfa_g` | 82 | 高血脂/饱和脂肪规则覆盖不全 |
| `sodium_mg` | 1 | 127/128 可用；缺失的是 `CN-1506` 椰子油 |
| `protein_g` | 4 | 营养汇总时必须返回不完整状态 |
| `fat_g` | 5 | 同上 |
| `carbohydrate_g` | 3 | 同上 |

过敏原状态为：已确认含 39、确认不含 83、未核查 6。`allergens` 为空不一定等于安全，必须结合 `allergen_status` 判断；现有数据未发现“已确认含但 token 为空”或“确认不含但仍有 token”的自相矛盾记录。

#### 与字段草案的差异

食材数据不能直接写入草案 `ingredient`，原因包括：

- 草案用 `SERIAL id`，文件之间实际依赖稳定的文本 `food_id`；应保留 `food_id UNIQUE NOT NULL`，内部可另设 identity 主键。
- `aliases`、`tags`、`allergens` 在 CSV 中是分号字符串，必须拆成 `TEXT[]`。
- `edible_pct` 应映射为 `edible_portion_pct`；`carbohydrate_g` 映射草案的 `carb_g`，建议数据库仍使用完整名称以避免歧义。
- 最新数据有 `state`、`source_url`、过敏原状态、嘌呤等级、脂肪酸字段，草案没有。
- 草案有 `cooked_factor`、`oil_absorption`、`source_id`、`version`、软删除和时间戳，当前食材文件没有，需允许 NULL 或由导入批次补齐。
- 微量营养素可按草案放入 JSONB，但钠、钾、钙、镁、胆固醇、饱和脂肪等被规则频繁引用，建议保留独立列；其余放入 `micro_nutrients` 和 `fatty_acids` JSONB。

### 4.2 做法规则

- CSV 和 JSON 都是 16 条、18 字段，逐值一致。
- JSON 中的 meta 与 YAML 完全一致。
- `rule_id`、标准做法名、别名均无重复。
- 16 条规则全部满足 `min ≤ default ≤ max`，油、盐、添加糖三个区间都未发现越界。

规则使用的是权威膳食指南提供的每日总量原则，再推导为项目内部的单菜估算区间。应在数据库中明确区分：

- `source_meta`：权威来源和总量原则；
- `oil/salt/sugar range`：工程估算，不应描述为官方测量值；
- `version`：算法或项目版本，调整区间时不能静默覆盖旧版本。

字段草案没有 `cooking_rule` 表，但菜库明确以 `cooking_rule_id` 外键引用它，所以这是必须新增的核心表。

### 4.3 家常菜库

- 30 道菜，127 条配料关联；菜 ID 无重复。
- 所有 `food_id` 都能在食材表找到，食材名完全一致。
- 配料中的每 100g 热量/蛋白质快照与食材表一致。
- 所有 `method` 和 `cooking_rule_id` 都能对应做法规则。
- 由 `oil_g`、`salt_g` 生成的油盐配料数量一致。
- 30 道菜的钠汇总均为完整值。
- `avoid.strict_allergens` 与从最新版食材表重算出的结果一致。
- 30 道菜全部为低油；盐等级为低 26、中 4。结构无误，但从业务丰富度看分布偏集中。

必须注意：

- 108 条配料级 `allergen_status` 过期。虽然 token 与最终严格排除结果正确，但程序如果直接读取配料快照状态，可能把已核查食材误判成“未核查”。
- 12 个汇总数相差 0.1，最大偏差仅 0.1，属于舍入策略不统一，不是原始食材关联错误。
- `nutrition_estimate` 和 `avoid` 都是派生快照，数据库的唯一事实来源应是 `food_id + amount_g + 当前食材版本 + 规则版本`。

与字段草案相比，`dish` 需要保留稳定的文本 `dish_id`、`cooking_rule_id`、`servings`、`nutrition_snapshot`、`avoid_snapshot` 和原始 JSON。`dish_ingredient` 还应保留 `role`、`generated_from` 和来源快照，草案里的 `is_optional` 可以默认 false。

### 4.4 RNI/AI/UL 参考摄入量

- 18 种营养素，448 条人群参考值；JSON 与 XLSX 逐值一致。
- 按完整组合键检查无重复。
- 只有两条 `value` 为空：膳食纤维 0–6 月、7–12 月。这两条应保留 NULL，不得填 0。
- JSON 还包含 `menstrual_status`、`note`、`type`、`ul`，字段草案未完整表达。
- Excel 中“铁 / 女 / 50–64”显示两行，分别是有月经 12 mg 与无月经 10 mg；如果忽略 `menstrual_status` 会错误去重。

草案中的 `age_min`、`age_max`、`sex`、`pregnancy`、`is_ai` 不足以表达最新版结构。建议至少使用：

`nutrient_id + sex + age_group + life_stage + menstrual_status + reference_type + value + ul_value + version`

其中 `reference_type` 取 RNI/AI，`ul_value` 独立存储，`life_stage` 包含普通、孕期各阶段、哺乳期等。年龄区间可以保留原始 `age_group`，并在能可靠解析时补 `age_min_months/age_max_months`。

### 4.5 营养素知识库

- 26 条营养素知识，无重复 ID，无缺失必填章节。
- 共 28 条参考资料：NIH ODS 24 条，另有 FDA、MedlinePlus、WHO、国家卫健委来源。
- RNI 的 18 个营养素 ID 在知识库中全部存在。

可直接做两层存储：

1. `nutrient_knowledge` 保存每条完整原始 JSONB，便于审计和页面展示；
2. 把“作用、缺乏表现、食物来源、注意事项”分别渲染成可读文本并切块，生成 `knowledge_doc`；确认嵌入模型维度后再加 pgvector 列。

不建议把知识 JSON 直接塞进草案 `knowledge_doc.content` 的单行，因为这会降低检索命中和引用定位质量。

### 4.6 禁忌规则

- 5 类慢病：糖尿病、高血压、高脂血症、痛风、肥胖/体重管理。
- 16 条慢病规则，10 条过敏规则，8 个参考来源。
- 所有引用 ID 均有定义，也没有未使用的引用。
- 对缺失值的处理原则正确：慢病规则要返回已知小计、缺失食材和完整度；过敏原“未核查”进入 `exclude_until_verified`，不能当作安全。

入库建议：首版先将整份 YAML 无损转换成 JSONB，存入版本化 `dietary_rule_set`，由 Agent B 按契约读取。待规则执行器稳定后，再决定是否拆成 `condition`、`rule`、`selector`、`reference` 等关系表，避免过早把嵌套结构拆得过细。

| `knowledge_doc` | 营养素知识 + 各说明文档 | 只有上游内容 | 需渲染、切块、生成稳定 key、向量化；确认 pgvector 维度 |

## 6. 哪些能直接导、哪些必须转换、哪些缺失

### A. 可直接导入“暂存层”

1. `食物成分表.csv` → `staging.food_raw`
2. `food_id映射表.csv` → `staging.food_id_mapping_raw`
3. `cooking_rules.csv` → `staging.cooking_rule_raw`

直接导入时全部使用 TEXT，空字符串转换成 NULL 的规则在下一步统一处理。这样某一行格式异常不会让整个原始证据丢失。

### B. 必须转换后进入核心表

- 食材 CSV：数值类型转换、分号字段拆数组、微量/脂肪酸组成 JSONB、补导入批次与来源。
- 菜谱 JSON：拆成菜表和配料关联表；刷新 108 条过敏状态；统一舍入；保留原 JSON 和派生快照。
- RNI JSON：把 18 个营养素下的 448 条 `values` 展平；保留 `menstrual_status/type/ul/note`。
- 营养知识 JSON：完整 JSONB 入原文表，再切块生成知识文档。
- 禁忌 YAML：无损转 JSONB；修正食材文件引用路径；和 `profile.conditions` 契约对齐。
- 做法 JSON/YAML：CSV 负责表格导入，JSON/YAML 负责 meta 和运行时发布版本，避免重复写两份事实记录。

### C. 压缩包中不存在的数据

- 用户档案、配餐方案、营养计算结果、周报、会话、消息等运行期数据；
- 经过专业审核的症状—营养素映射；
- 切块后的知识文档及 embedding；
- 生重到成品换算系数、油吸附系数的系统性数据；
- 完整的活动水平计算规则；
- 自动化验收测试样例、验证脚本、统一来源登记册。

另外，根说明提到的 `rni_reference_adult.json` 实际不存在；不能在导入脚本里依赖它。

## 7. 推荐的数据库分层

建议不要把所有表都放在 `public`：

- `staging`：原始 CSV/JSON/YAML 的暂存副本；可重跑、不可直接供业务查询。
- `core`：食材、营养素、RNI、菜谱、做法规则、禁忌规则等稳定主数据。
- `app`：用户画像、配餐、营养计算、周报、会话消息。
- `knowledge`：营养知识原文、切块后的知识文档和向量。
- `audit`：导入批次、文件摘要、数据问题和发布状态。

关键主键策略：

- 数据库内部使用 `GENERATED BY DEFAULT AS IDENTITY`，不要在新项目里继续用 `SERIAL`。
- `food_id`、`dish_id`、`rule_id`、`nutrient_id` 是跨文件稳定业务键，必须加 UNIQUE 或直接作为自然主键。
- 派生快照必须同时记录导入批次、食材数据版本和规则版本，才能重算和追责。

具体表结构已另附 `02_PostgreSQL建表与导入顺序草案.sql`。其中只包含建表建议，不会自动修改当前数据库。

## 8. 推荐的导入步骤

### 第 1 步：原件归档

- 保留原 ZIP，不改名、不重新压缩、不删除内部文件。
- 登记文件名、SHA-256、收到日期、数据版本和负责人。
- 如需交接，另做一个清除 `__MACOSX`/`.DS_Store` 且使用 UTF-8 文件名的“干净副本”。

### 第 2 步：只建结构，不导正式表

- 建立 `audit/staging/core/app/knowledge` 五个 schema。
- 先建 `import_batch`、暂存表、来源表、营养素维表。
- 再建食材、做法、菜谱、RNI、规则、知识及业务空表。

### 第 3 步：装载暂存层

- CSV 用 `\copy`，所有列先作为 TEXT。
- JSON/YAML 由导入脚本写入 `staging.document_raw.payload JSONB`。
- 每行记录 `import_batch_id` 和 `row_no`。

### 第 4 步：运行质量门禁

至少验证：

- 食材 128 条、46 字段；`food_id/name` 唯一；无负数；可食部 0–100。
- 食材 CSV 和 JSON 逐值一致。
- 做法规则 16 条；三个区间均满足 min≤default≤max。
- 菜 30 道、配料 127 条；全部外键可解析；方法与规则匹配。
- RNI 18 种、448 条；完整组合键唯一；两个婴儿膳食纤维值保持 NULL。
- 过敏原状态与 token 逻辑一致；所有菜的配料状态从最新版食材表重算。
- 所有“缺失”保持 NULL，不能在 SQL 中使用 `COALESCE(value, 0)` 做营养结论。

### 第 5 步：事务性写入核心表

建议依赖顺序：

`data_source → nutrient → ingredient → food_id_mapping → cooking_rule → nutrient_reference → dish → dish_ingredient → dietary_rule_set → nutrient_knowledge → knowledge_doc`

任何 P0 检查不通过，都回滚本批次；不要把“部分成功”静默发布成最新版本。

### 第 6 步：验收与发布

- 对每张核心表核对行数、空值、唯一键和外键。
- 抽查至少 5 道菜按 `food_id + amount_g` 重算热量、蛋白质、钠和过敏原。
- 抽查 RNI 的儿童、成人、孕期、哺乳期、50–64 岁女性月经状态。
- 将导入批次状态从 `loaded` 改为 `validated`，最终通过后改为 `promoted`。
