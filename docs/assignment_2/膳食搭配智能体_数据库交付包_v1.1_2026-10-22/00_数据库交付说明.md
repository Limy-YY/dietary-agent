## 怎么恢复

推荐直接使用备份文件：

```bash
createdb diet_agent
pg_restore --no-owner --no-privileges -d diet_agent 03_数据库备份_diet_agent_v1.1.dump
psql -d diet_agent -f 09_数据库安全配置.sql
psql -d diet_agent -f 08_数据库验收.sql
```

也可以用SQL文件恢复：

```bash
createdb diet_agent
psql -d diet_agent -f 01_数据库结构.sql
psql -d diet_agent -f 02_基础数据.sql
psql -d diet_agent -f 09_数据库安全配置.sql
psql -d diet_agent -f 08_数据库验收.sql
```

最后看到 `DATABASE DELIVERY ACCEPTED`，说明恢复和数据量都正常。

如果已经恢复过v1.0，不需要重建数据库，执行：

```bash
psql -d diet_agent -f 13_食材数据更新_v1.1.sql
psql -d diet_agent -f 08_数据库验收.sql
```

## Schema怎么分

- `core`：食材、菜式、营养素、参考值和规则。
- `knowledge`：营养知识和知识文档。
- `app`：业务空表、查询视图和函数。
- `audit`：导入批次和质量问题。

`staging` 是导入过程使用的暂存层，没有放进正式交付。

## 需要注意

- 用户、餐单、营养结果、周报和对话表交付时都是空的。
- 前面做的虚构测试数据没有放进这个包。
- 原始禁忌规则已完整入库，包括5组慢病、16条慢病规则、10条过敏规则和8个来源。
- 另外已把4条高血压规则整理成可审核、可追踪的结构化规则，并登记国家卫健委、WHO和NHLBI DASH来源。
- 这些规则当前处于“已入库、待专业审核”状态，暂不进入生产自动判断；审核通过后可以按流程启用。
- 数据缺失仍保留为 `NULL`，后端不要当成0。
- HTTP接口和JSON格式由后端与Agent开发一起定，不属于本次数据库交付。
- 应用不要使用数据库超级用户连接。

更详细的核查过程放在 `reference/`，平时接入不用先看那些文件。
