## 二、逐项实现与验证

### B1 快捷追问透传

**任务书说法与实测不符的两处**（按实测改了）：

1. Agent 侧 done 事件原本没有 `suggestions` 字段，不是"已下发"；
2. 前端也没有渲染，`lastSuggestions` 只定义未消费，不是"已完成渲染"。

**改动**

- `agent/agent.py`：新增 `_suggestions(result)`，按方案卡片状态（draft/fixed）、档案缺失、报告场景分组生成；`run()` 包装 `_run` 后 `result.setdefault("suggestions", ...)`。
- `agent/main.py`：done 事件加 `"suggestions": result.get("suggestions") or []`。
- `backend/routers/chat.py`：新增 `_normalize_suggestions()`（兼容字符串数组与对象数组，去重，最多 4 条）；`_agent_events` 不再丢弃 Agent 的 done，改为 `yield "suggestions"`；自建 done 携带 `suggestions`。
- 前端：`chat.js` 把 done 的 suggestions 写入 `aiMsg.suggestions`；`ChatMessage.vue` 增加 `suggestions` computed（取 `text/label/content/phrase`）与气泡下方 chip，点击 `$emit('phrase')` → `ChatPane` 的 `@phrase="send"`。

**验证**

- SSE 实测 `POST /api/agent/chat {"user_id":"demo-user","message":"你好"}` → done 返回 `["排今天的三餐","排一周的餐","查营养素推荐量"]`（字符串数组与对象数组两种形态都被归一化）。
- 浏览器实测（vite dev + Chrome headless）：chip 3 个正常渲染，点击「排今天的三餐」后用户气泡出现该短语且进入「正在生成配餐方案」，控制台 0 错误。截图：`frontend/docs/screenshots/b1_suggestion_chips.png`。
- 点击后的链路真的走到底了：该次点击为 `demo-user` 生成了方案 75（2026-11-25 单日，status=candidates，带 3 条 `nutrition_tips`），即 chip → 发送 → Agent 排餐 → 落库 → 面板可读，整条链通。

### B2 营养提示落库

**口径**：配餐（`_persist_plan`）时生成一次写入方案字段；确认（`week/fix`）时仅在字段为空时兜底生成；面板只读，不在请求时实时生成。

**改动**

- 库：`app.meal_plan.nutrition_tips jsonb NOT NULL DEFAULT '[]'`（脚本 63 号，幂等，含回滚语句与验证 SQL）。
- **与主线前端契约对齐**：主线前端已由 F9（IMP-070）实现 `normalizeNutritionTips`，只读 `title / text / source` 三个字段并据此单行渲染。后端每条提示除保留完整结构化字段（`nutrient_id / daily_amount / reference_value / coverage_pct / function / deficiency / sources` 等），同时输出 `title=营养素名`、`text=量化结论＋作用＋缺乏后果＋富含来源`、`source="DRIs 2023"`，保证主线面板不改代码就能显示三要素；否则 `text` 为空会被 `filter(Boolean)` 整条丢掉、面板显示空白。
- `models/meal_plan.py`：加 ORM 字段。
- `mealplan.py`：新增 `_build_nutrition_tips(db, plan)` 与 `_tip_age_group/_tip_sex/_tip_status/_tip_payload` 辅助；`_persist_plan` 在候选落库后赋值；`week/fix` 空值兜底；`_serialize_plan` 输出 `nutrition_tips`。
- 前端：`schema.js::normalizeCurrentPlan` 透出并归一化（`normDeficiency` 把 `deficiency` 的 `interpretation` + `possible_manifestations` 摊平成 `note` + `items`）；`CurrentPlanPanel.vue` 在「方案概览 → 营养提示 → 食谱概览」位置渲染三要素，状态标签配色区分缺口/部分覆盖/已覆盖。

**生成逻辑**

| 环节 | 做法 |
|---|---|
| 营养素范围 | 已选候选 `micro_estimate` 的 7 项（钙/铁/锌/维A/B1/B2/维C） |
| 汇总 | 非空值累加后按覆盖天数折算日均；缺失记 `missing_slots`，**不按 0 计** |
| 参考量 | `core.nutrient_reference` 同年龄段 RNI（无 RNI 取 AI），性别按档案（`female`/`女` 两种写法都识别），识别不出用 both |
| 科普三要素 | `knowledge.nutrient_knowledge.payload` 的 `function` / `deficiency` / `sources` |
| 排序 | 覆盖率升序取前 3，即"差距最大的 3 个" |
| 可信度 | 已安排餐次目标热量 / 全天目标 < 0.8 → 状态降为「部分覆盖」并提示日均不代表全天 |

**验证**

- 单日三餐（方案 74，TEST-E2E-05，目标 1762.6 kcal）：落库 3 条，概览热量占全天 99.99% → 状态为「低于参考量 / 已覆盖 / 已覆盖」，维B1 日均 0.9mg vs RNI 1.2mg = 75%。
- 多日单餐（方案 73，每天 1 餐午餐）：概览热量占全天 40% → 3 条状态均为「部分覆盖」，钙 459.75mg = RNI 800 的 57.5%（396.9+522.6 两天折算，可手算复现）。
- `GET /api/meal-plan/74` 返回 3 条含 `function/deficiency/sources/headline/coverage_pct` 等字段。
- `POST /api/meal-plan/week/fix` 后 status=fixed，tips 仍 3 条、`coverage_pct` 75/133.3/160 与原值一致（未重算）。
- 浏览器实测渲染 3 张卡片、9 个区块标签、20 个来源 chip、0 控制台错误。截图：`frontend/docs/screenshots/b2_nutrition_tips.png`。
- 单餐方案（TEST-E2E-05，2026-11-27 早餐，candidates）：3 条均为「部分覆盖」，每张卡脚注「本方案未覆盖全天餐次，日均仅供量级参考」，与 25% 热量占比一致。截图：`frontend/docs/screenshots/b2_current_plan_panel.png`。该测试方案验证后已清理。

**面板时间显示（本次一并修）**

- 现象：`updatedText` 只读 `plan.fixed_at`，草稿/待确认态固定时间为空 → 面板顶部显示「更新于 —」。
- 改法：`schema.js` 透出 `updated_at`（后端 `_serialize_plan` 本来就输出该字段，只是前端没接）；`CurrentPlanPanel` 改为已生效读 `fixed_at`、其余读 `updated_at`（回退 `fixed_at`）。
- 验证：candidates 方案面板显示「更新于 2026-11-26 13:39」，不再是「—」；fixed 方案仍显示「固定于 …」。

### B3 当前规划接口语义

`current_plan` 改为内部 `_latest(status)` 各取最新，再比较 `created_at`：草稿更新于固定方案则返回草稿，反之返回固定方案。

验证：测试档案 + 两条方案（900001 fixed 旧、900002 candidates 新）——场景 A 返回 900002/candidates，把 fixed 时间改到最新后场景 B 返回 900001/fixed。测试数据已清空。

### B4 知识检索中文召回增强

**根因两层**

1. 关键词路 `query.split()` + 整串 `ILIKE '%整句%'` + AND，中文无空格查询必然 0 命中；
2. 向量路其实是空的：`knowledge.knowledge_doc` 43 篇文档 `with_emb=0`，全库无 embedding，hybrid 每次都退化为 keyword_fallback。

**改动**

- `agent.py`：jieba（`cut_for_search`）分词，缺包退 2-gram；约 60 条中文停用词；`_tokenize` 保留单字实词（专门解决「维生素D」的 D 被误丢）；`_score_terms` 按 title 0.9 / content 0.7 / category 0.5 打分，停用词只召回不计分；`_search_knowledge` 改为 ILIKE OR 召回（LIMIT 300）+ Python 打分排序 + `nutrient_knowledge` 补位。
- 向量回灌：`GRANT UPDATE ON knowledge.knowledge_doc TO diet_backend`，用 `database/15_RAG灌库脚本.py` 灌 43 条（0 失败，2 次 API 调用 / 12177 字符）；灌后 `with_emb=43, dim=1024`，相似度 0.5~0.77。
- `requirements.txt` 追加 `jieba>=0.42`。

**验证**：「低GI 主食怎么选」改前 0 条 → 改后 hybrid_rrf 5 条；「钙每天补多少」参考值条目排第一；「维生素D 缺乏有什么后果」维生素D 排第一；「减脂期早餐吃什么」减重期排第一。

### B5 召回参数调优

- 先修 `backend/tests/eval_recall.py` 自身两处 bug：SQL 缺 CAST（`function ... does not exist`）、标注 slug 写错（`nutrient:fiber:overview` → `nutrient:dietary_fiber:overview`）。
- 24 条问句 × 4 阈值：**0.3 / 0.4 / 0.5 的 recall@5 均为 100%，0.6 降到 91.67%**（「平衡膳食餐盘怎么搭」「全谷杂粮怎么当主食」返回空）。结论：现有 0.5 已是最优，不下调。
- `config.py` 新增并外置 `RAG_MIN_SIMILARITY=0.5`、`RAG_TOP_K_DEFAULT=5`、`RAG_POOL_MULTIPLIER=4`（后者仅作文档记录），`agent.py` 的 `min_sim` 改读配置。

### B6 JWT 密钥加长

- `backend/.env` 的 `JWT_SECRET` 由 23 字节占位串轮换为 `secrets.token_urlsafe(48)` 生成的 **64 字符**随机串（脚本原地替换，不回显明文）；`config.py` 默认值改为 `dev-only-placeholder-change-me-32bytes`。
- 验证：新 token 访问 `/api/meal-plan/current` → 200；用旧密钥离线签的 token → 401。
- 连带修复：`docs/testing/automation/` 下 5 个脚本（verify_live / verify_executed / verify_issue7 / verify_auth_edge / verify_gd3_live）原本硬编码旧密钥，换钥后必然全挂。新增 `jwt_secret.py` 统一读取（`LIVE_JWT_SECRET` 环境变量 → `backend/.env`），5 个脚本改为调用它；复验 `verify_live.py` 与 `verify_gd3_live.py` 新签 token 访问真实接口均 200。

### B7 营养参考值接入问答检索

- `schemas/agent.py`：`RagItem` 加 `kind` 与 `reference: dict | None`；`kind` 枚举为 `doc | nutrient | reference | notice`。
- `agent.py`：新增 `_REFERENCE_DEFAULT_AGE_GROUP="18-29"`、`_REFERENCE_SOURCE_NAME`、`_REFERENCE_SOURCE_ID`、`_match_nutrients()`（`core.nutrient.name_zh` 括号外主名 + `payload.aliases`（≥2 字符）匹配）、`_fmt_num()`、`_search_nutrient_reference()`（先取全量分层再挑成人代表值，`reference.layers` 只挂第一条避免重复）；`rag_query` 改为 reference 优先 + 原检索结果补齐，受 `top_k` 约束。
- **无参考值营养素改为显式提示**：库内 8 种（叶酸 / ω-3 / B12 / B5 / B6 / B7 / 维生素D / 维生素K）没有参考值行，原实现 `continue` 静默跳过，用户问了会得到"没这回事"的错觉。现改为追加一条 `kind=notice` 的条目置顶，正文明确"本营养素 RNI/AI 尚未入库，**本节不给数值**，需要按参考量安排请以《中国居民膳食营养素参考摄入量（2023）》原文为准"，再接正常知识文档，避免被 Agent 当成数值引用。
- 验证：
  - 「钙每天补多少」→ 首条 `[reference] 营养参考值：钙（成人） | RNI 800 mg/天；UL 2000 mg/天`（有数据的营养素不受影响）。
  - 「铁」→ 女 18mg / 男 12mg 两条；「维生素A」→ 女 660 / 男 770 μg RAE。
  - 「叶酸每天需要多少」→ 首条 `[notice] 叶酸：库内暂无参考值`，其后补叶酸/B12/孕期营养要点/B2 文档，`method=hybrid_rrf`。
  - 「维生素D 每天补多少」→ 首条 `[notice] 维生素D：库内暂无参考值`，其后补维D/全谷杂豆/维E/镁文档。

## 三、遗留项处置与结论

| 事项 | 结论 | 依据 |
|---|---|---|
| B5 的检索池大小与两路权重 | **不改** | 参数写在 `knowledge.search_documents` 函数内部（`p_limit*4`、`1.0/(k+rank)` 两路等权），属共享库对象变更、需走评审；且 recall@5 在 0.3/0.4/0.5 已均 100%，改池与权重无实测收益，只增回归风险 |
| 参考值总数 448 vs 447 | **已查明：任务书写错，实为 447** | 源文件 `database/27_rni_reference_铁源单行修订.json` 逐营养素 `values` 计数为 24×13 + 26×2 + 28×2 + 27 = **447**；库内按 nutrient 分组比对 `expected_total 447 / actual_total 447 / mismatch: none`，零差异，不存在漏灌 |
| 8 种营养素无参考值 | **已改为显式提示**（见 B7） | 返回 `kind=notice` 置顶条目 + 明确"不给数值"，叶酸/维生素D 实测通过 |

| 方案生成耗时 | **已复测：属冷启动，不是常态** | 服务重启后首次 `week/generate` 单日三餐 >60s（客户端超时先报错、服务端最终成功）；服务热态下同日复测单餐 **1 秒**返回。结论：慢在进程冷启动加载规则与菜库，未做启动预热优化（非任务书要求） |

| 测试方案数据 | 方案 74 保留、方案 76 已清、方案 75 属演示数据保留 | 74 是 B2 完整验证样本（fixed + 3 条 tips），留作复核；75 是 demo-user 在 B1 前端验证时点「排今天的三餐」真实生成的方案（candidates + 3 条 tips），属演示轨迹，保留；76 为本次面板时间验证临时生成，验证后按层级删除（plan 1 / slot 1 / candidate 3 / candidate_dish 8 / shopping 0） |
| 存量方案 `nutrition_tips` 未回填 | **不回填，符合设计** | B2 要求"生成一次、面板只读"，历史方案（如方案 73）保持 `[]` 是其应有状态 |
