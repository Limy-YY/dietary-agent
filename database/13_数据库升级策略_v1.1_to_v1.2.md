# v1.1 → v1.2 升级策略说明

对应评审意见：P2-1「补交增量升级脚本」。

## 结论先讲

**v1.1 到 v1.2 不走增量 SQL，整库重灌是唯一受支持的升级方式。**

评审原文允许"补交增量升级脚本，或明确'整库重灌'为唯一恢复方式"这两条路取其一。
本项目选后者，理由不是省事，是另外三条路都站不住：

1. **没有 v1.1 的结构基线。** 交付范围里只有 v1.2 这一个包，v1.1 的 dump、结构 SQL、字段口径都不在手上。
   任何"ALTER TABLE ... 从 v1.1 改成 v1.2"的脚本都是照着 v1.2 的现状反推 v1.1 长什么样，
   反推错一个列名，脚本就会在真实 v1.1 库上中途停下——而且停在一个已经改了一半的库上。
2. **新增 30 道菜的配料明细只存在于 01 dump 里。** `core.dish` 的 30 道新菜与 `core.dish_ingredient`
   的 127 条新关系，源数据表汇总里只有菜名与部分营养，没有逐条配料与克数。增量脚本要么把这些
   数据硬编码成 INSERT（等于把 dump 里的数据再抄一遍，两份副本必然漂移），要么只改结构不补数据
   （那 v1.2 的 60 道菜在升级后的库上根本凑不齐）。
3. **v1.1 与 v1.2 的差异覆盖到约束层。** v1.2 引入了四级状态机（meal_plan / meal_slot /
   meal_candidate / meal_candidate_dish）与 fixed 后只读触发器，还改了 conditions 的承载方式
   （jsonb 对象）。这些不是加几列能补齐的，硬做就得重建表并搬数据，代价高于直接重灌，
   风险也高于直接重灌。

## 受支持的升级路径（v1.1 → v1.2r1）

```bash
# 1) 备份现网 v1.1 库（留着回滚用，不参与升级）
pg_dump -Fc -h <host> -p <port> -U <superuser> -d diet_agent_v11 > diet_agent_v11_$(date +%Y%m%d).dump

# 2) 建一个新库，整库恢复到 v1.2
createdb -h <host> -p <port> -U <superuser> diet_agent
pg_restore --no-owner --no-privileges --exit-on-error \
  -h <host> -p <port> -U <superuser> -d diet_agent \
  01_完整数据库备份_diet_agent_v1.2_60道菜.dump

# 3) 打本轮整改（v1.2 → v1.2r1）
psql -h <host> -p <port> -U <superuser> -d diet_agent -f 12_数据库整改_v1.2_to_v1.2r1.sql

# 4) 账号与权限（必须在 12 之后）
psql -h <host> -p <port> -U <superuser> -d diet_agent -f 03_应用账号与权限.sql

# 5) 验收
psql -h <host> -p <port> -U <superuser> -d diet_agent -v ON_ERROR_STOP=1 -f 04_数据库整体验收.sql

# 6) 切流：应用连接串指向新库；确认无误后再回收旧库（先别删，观察一周）
```

采用"新库起、旧库留"的方式而不是原地升级，代价是多一份磁盘，收益是回滚只需改连接串。

## 已经存在的 v1.2 库怎么升到 v1.2r1

不需要重灌，执行 `12_数据库整改_v1.2_to_v1.2r1.sql` 即可，脚本幂等，重复执行无副作用：

```bash
psql -h <host> -p <port> -U <superuser> -d diet_agent -f 12_数据库整改_v1.2_to_v1.2r1.sql
```

这个脚本做四件事：P1-1 的 conditions 契约（函数 + NOT VALID 的 CHECK + 旧字段注释 + 兜底视图）、
P2-3 的食材检索 5 字段（重写视图与函数）、P3 的清理（删 staging、删虚构测试视图、legacy 方案打保留标记）、
以及迁移登记与授权。逐条对照见 17。

## 如果业务方坚持"不许重灌"

那也有一条边界清晰的做法，但请把它理解为**尽力而为**，不是本包的验收承诺：

1. **先对齐结构**：在 v1.1 库上按 02 的结构文件逐 schema 比对，补出 v1.2 新增的表、列、函数、触发器与约束
   （唯一可以机械照搬的是结构与约束，数据不能照搬）。
2. **再迁"纯配置类"数据**：下面这些表的内容在 v1.1 与 v1.2 之间语义一致，可以整表导出再导入：

| 表 | 内容 | 迁移注意 |
| --- | --- | --- |
| `core.nutrient` | 营养素定义 | 主键 nutrient_id 稳定，可直接导 |
| `core.health_condition` | 疾病/目标定义 | 注意 v1.2 的 activation_status 默认值 |
| `core.condition_nutrient_rule` | 疾病营养规则 | v1.2 新增 review_status/is_active，导入后需重新走医学审核 |
| `core.goal_structure_map` | 目标结构映射 | 5 条，可直导 |
| `core.data_source` | 数据来源登记 | 导完再导食材，否则来源外键为空 |
| `knowledge.*` | 知识文档与营养素知识 | 文本类，可直导；向量列在 v1.2r1 才建，导入后再灌 |

3. **食材与菜式要么全导要么不导**：`core.ingredient`、`core.dish`、`core.dish_ingredient` 三张表互相咬合
   （配料关系靠 food_id / dish_id 关联），且带逐行 `source_row` 溯源。v1.1 里没有的 30 道菜与 127 条关系
   只能从 01 dump 里取——这就是为什么第 2 条只列了配置表。
4. **迁移完必须验的项**：`core.ingredient` 的 128 行、`core.dish` 的 60 行、`core.dish_ingredient` 的 254 行、
   5 条目标映射、7 条关键微量，以及 `app.v_ingredient_search` 的 25 列与 `search_ingredients` 的 18 个出参
   （04 的 1b 段会逐项查）。
5. **重灌后必须再跑一次 12**：R2 把"女 / 50-64"的铁参考从两行并成一行，这属于数据修订，
   重新灌库会把它覆盖回两行（源文件 `rni_reference.json` 目前仍是两行）。12 的 R2 块是幂等的，
   重灌后跑一遍就回到单行取 12 的状态，04 的 2b 段会验这一点。
6. **用户数据（app.*）不要迁**：v1.1 的 profile 是旧字段（sex / goal），v1.2 是 conditions jsonb 对象。
   v1.2r1 有 `app.v_profile_effective` 做兜底读取，但历史计划、餐位、候选在 v1.1 里没有对应结构，
   迁过来只能填默认值，provenance 全丢。老计划按"只读归档"处理更干净。

## 为什么不建议"结构对齐 + 只补结构"

评审在意的是"能不能把 v1.1 安全带到 v1.2"。只补结构不补数据的结果是：库能起来、验收能跑，
但 60 道菜凑不齐、5 条目标映射缺失，产品功能直接降级。与其交付一个"结构对、数据空"的半成品，
不如明确告诉运维：整库重灌，十分钟的事。
