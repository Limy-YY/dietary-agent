# 空库恢复与复跑说明

对应评审意见：P3「05 与 08 两个结果文件字节相同」。

## 先说结论

原来的 `08_空库恢复测试结果.txt` 与 `05_数据库整体验收结果.txt` 逐字节相同（sha256 一致）。
这说明当年做 08 时并不是在另一个空库上重新恢复、重新跑一遍验收，而是把 05 的结果复制了一份改个名字。
所以 08 不能作为"备份恢复了、恢复后也验收过"的证据，本轮把这层假象撤掉：

- 文件本身不再保留（内容与 05 的附录 A 完全重复，没有独立信息）；
- 恢复能力的证据改由两部分承担：01 dump 本身可用、05 里记录的"用结构脚本重建 + 全量断言"实测；
- 真正的空库恢复复跑步骤写在下面，任何一台装了 PostgreSQL 18 客户端的机器都能照做。

## 为什么这一轮没能补一次真正的空库恢复

本机（Windows 台式）没有 PostgreSQL 服务端，也没有 `psql` / `pg_dump` / `pg_restore`：

- EDB 官方 Windows 免安装包在当前网络环境下全部 403／连接被拦；
- 从 Maven Central 取到的 `embedded-postgres-binaries 18.6.0` 只含 `initdb.exe`、`pg_ctl.exe`、`postgres.exe`，
  不含客户端工具，因此 `pg_restore` 这条路在本机走不通；
- 本机无 Docker、无 WSL 发行版，也没有第二条能装出 `pg_restore` 的路。

在这样的条件下，写一份"空库恢复成功"的结果文件只能是编的。所以本轮改交：
① 01 dump 的真实格式与版本信息（见下）；② 结构层面的等价重建实测（见 05 第二节）；
③ 一份可被任何人复现的复跑清单（见下）。

## 空库恢复复跑步骤（在任意装有 PG18 的机器上）

```bash
# 1) 建一个全新的空库，不要复用已有库
createdb -h <host> -p <port> -U <superuser> diet_agent_restore_check

# 2) 先只列出归档内容，确认对象与版本对得上（不写库）
pg_restore -l 01_完整数据库备份_diet_agent_v1.2_60道菜.dump | head -40

# 3) 正式恢复
pg_restore --no-owner --no-privileges --exit-on-error \
  -h <host> -p <port> -U <superuser> -d diet_agent_restore_check \
  01_完整数据库备份_diet_agent_v1.2_60道菜.dump

# 4) 打上本轮整改（v1.2 → v1.2r1）
psql -h <host> -p <port> -U <superuser> -d diet_agent_restore_check -f 12_数据库整改_v1.2_to_v1.2r1.sql

# 5) 建应用账号与权限（整改脚本先跑，授权才会带上新对象）
psql -h <host> -p <port> -U <superuser> -d diet_agent_restore_check -f 03_应用账号与权限.sql

# 5b) 补 4 个病种字典（不跑的话前端存另外三种病会 400、Agent 建档 422）
psql -h <host> -p <port> -U <superuser> -d diet_agent_restore_check -v ON_ERROR_STOP=1 \
  -f 18_病种字典补齐_v1.2r1.sql

# 6) 验收：这一步在含数据的库上执行，数据计数类断言才会转绿
psql -h <host> -p <port> -U <superuser> -d diet_agent_restore_check -v ON_ERROR_STOP=1 \
  -f 04_数据库整体验收.sql | tee 08_空库恢复复跑输出_$(date +%Y%m%d).txt

# 7) 灌 RAG 向量（可选，需要 pgvector，见 16）
psql -h <host> -p <port> -U <superuser> -d diet_agent_restore_check -f 14_RAG向量化_v1.2r1.sql
python 15_RAG灌库脚本.py --dry-run
```

## 复跑时的三个坑

1. **顺序建议 12 → 03**。`03` 是"对当时存在的对象逐个授权"，放在 `12` 之后，整改新增的
   `v_profile_effective`、`is_condition_map_valid` 与重建后的 `search_ingredients` 才会一次授权到位。
   反过来也能跑（`12` 里有 diet_app 存在即补授权的 DO 块，`03` 还有默认权限兜底），
   但容易漏掉个别新对象，事后要手工补 GRANT。
2. **04 必须用 r1b 版**（本包这份）。旧版第 7 段还在查 `app.v_condition_rule_branch_acceptance`，
   那个视图已被 12 删掉，旧脚本会直接报 `relation does not exist`；这一版同时把 1b 改成 18 出参、
   加了 2b 的 R2 数据断言。
3. **`pg_restore` 要 18**。PG17 及更早的 pg_restore 读 1.16 归档会报
   `unsupported version (1.16) in file header`，这不是备份损坏，是工具太旧。

## 如果只想确认备份没坏（不做恢复）

```bash
pg_restore -l <dump> > /dev/null && echo "归档目录可读，文件完整"
```

`-l` 只读归档的目录表（TOC），不解压数据，是最轻的完整性检查；但它不能替代一次真实恢复。
