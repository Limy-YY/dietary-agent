# 知识库向量灌库 · 使用说明

> 配套脚本：`database/64_知识库向量灌库.py`（向导）、`database/灌库.bat`（双击）、`database/15_RAG灌库脚本.py`（真正的灌库引擎）
> 背景：PR #25 验收时发现，重建出来的 222 库 `knowledge.knowledge_doc` 43 篇全部 `with_emb=0`，混合检索退化成关键词，B4 的向量路等于没开。

---

## 一、为什么要有这层包装

`15_RAG灌库脚本.py` 本身是完整的（幂等、按内容 hash 判断重灌、失败重试、支持 `--dry-run`），但它要手工准备 6 个环境变量：

```
PGDSN / EMBEDDING_BASE_URL / EMBEDDING_MODEL / EMBEDDING_DIM / EMBEDDING_MODE / EMBEDDING_API_KEY
```

换个人、换台机器、重开一个终端，就得重来一遍，还容易把 key 漏在 shell 历史里。

`64_知识库向量灌库.py` 只做三件事：**从 `backend/.env` 读配置 → 缺什么交互补什么（key 打码）→ 写回 `.env`，然后调 15**。配一次，以后 `--run` 就走。

---

## 二、第一次用（队长操作）

Windows 双击 `database/灌库.bat`，或命令行：

```bash
cd database
python 64_知识库向量灌库.py
```

会看到：

1. 打印当前配置（key 脱敏成 `sk-abc***（51 字符）`）；
2. 缺 `EMBEDDING_API_KEY` 就提示输入，**输入时不回显**；
3. 存进 `backend/.env`（写前自动备份成 `.env.bak-20261126203000`，该文件已在 `.gitignore`）；
4. 自动体检：连库 → 打印「文档 43 篇 / 已有向量 0 篇 / 待灌 43 篇」→ 调一次 embedding 验证 key；
5. 问「现在开始灌库？（y/N）」，y 直接跑。

灌库过程会显示每批进度，最后复查一次向量数。

## 三、之后的日常用法

| 命令 | 作用 | 花不花钱 |
|---|---|---|
| `python 64_知识库向量灌库.py --check` | 体检：配置 + 连库 + 调一次 embedding | 一次极小调用 |
| `python 64_知识库向量灌库.py --check --no-probe` | 只查配置和库，不碰网络 | 不花 |
| `python 64_知识库向量灌库.py --dry-run` | 统计待灌条数与预估调用量 | 不花 |
| `python 64_知识库向量灌库.py --run` | 用已存配置直接灌，不再交互 | 按条数 |
| `python 64_知识库向量灌库.py --set-key` | 只换 Key（打码），不动别的 | 不花 |
| `python 64_知识库向量灌库.py --run --batch-size 16 --limit 10` | 小批试跑 | 按条数 |

**幂等**：15 脚本按内容 md5 判断，已经灌过且内容没变的文档不会再调模型，重复跑安全。

**CI / 服务器**：没有交互终端时，用环境变量兜底即可，不用写 `.env`：

```bash
export EMBEDDING_API_KEY=sk-xxx
python 64_知识库向量灌库.py --run -y
```

## 四、前置条件

| 项 | 要求 |
|---|---|
| 库 | 已建好，且有 `knowledge.knowledge_doc.embedding` 与 `knowledge.v_embedding_backlog`（来自 `14_RAG向量化_v1.2r1.sql`） |
| 维度 | `EMBEDDING_DIM` 必须等于 embedding 列维度（当前 **1024**），不一致时脚本会直接拦下，不会灌废数据 |
| Python | 3.10+，且装了 `psycopg`：`pip install "psycopg[binary]>=3.1"` |
| 网络 | 能访问 `EMBEDDING_BASE_URL`（默认硅基流动） |

## 五、灌完怎么验

```sql
-- 1) 覆盖率：应当 43/43
SELECT count(*) AS docs, count(*) FILTER (WHERE embedding IS NOT NULL) AS with_emb
  FROM knowledge.knowledge_doc;

-- 2) 待灌队列：应当 0
SELECT count(*) FROM knowledge.v_embedding_backlog;
```

再打一次检索，看是否从「关键词退化」回到混合检索：

```bash
curl -s -X POST http://127.0.0.1:8000/api/agent/rag-query \
  -H "Content-Type: application/json" \
  -d '{"query":"低GI 主食怎么选","top_k":5}'
```

灌之前 top1 是「糖尿病与血糖偏高人群膳食要点」（关键词碰巧命中），灌之后应当能命中「全谷杂豆与主食替换」这类直接相关的文档。

## 六、常见报错

| 现象 | 原因 | 处理 |
|---|---|---|
| `HTTP 401 Token is invalid` | key 错/过期 | `--set-key` 换一个 |
| `返回维度 768 与配置 1024 不一致` | 模型换了但维度没改 | 改 `EMBEDDING_DIM`，或换回 `bge-m3` |
| `relation "v_embedding_backlog" does not exist` | 14 脚本没执行 | 先跑 `14_RAG向量化_v1.2r1.sql` |
| `连不上或缺少对象` | 库没起 / `DATABASE_URL` 端口不对 | 默认容器 5432，独立验证实例是 5433 |
| 灌完 `with_emb` 还是 0 | 走了 `--emit` 或中途失败 | 看 15 脚本输出的失败批次，重跑即可（幂等） |

## 七、顺带建议（给数据岗）

重建链路目前不会灌向量，所以**每次空库重建后都要手工跑一次本脚本**，否则 RAG 静默退化成关键词。建议：

1. 在 `docker/initdb/` 之后加一步可选的 `59z_embedding.sh`（读环境变量里的 key，没有就跳过并打印提醒）；
2. 或在 `/api/health` 里暴露 `knowledge.with_emb`，让「向量没灌」变成一眼可见的状态，而不是等检索质量下降才发现。
