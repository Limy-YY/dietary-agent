## 二、部署顺序（顺序错了会出问题）

```bash
createdb diet_agent
pg_restore --no-owner --no-privileges --exit-on-error -d diet_agent 01_完整数据库备份_diet_agent_v1.2_60道菜.dump
psql -d diet_agent -v ON_ERROR_STOP=1 -f 12_数据库整改_v1.2_to_v1.2r1.sql      # 必须早于 03
psql -d diet_agent -v ON_ERROR_STOP=1 -f 03_应用账号与权限.sql
psql -d diet_agent -v ON_ERROR_STOP=1 -f 18_病种字典补齐_v1.2r1.sql     # 补 4 个病种，后端 _check_conditions 依赖
psql -d diet_agent -v ON_ERROR_STOP=1 -f 04_数据库整体验收.sql
```

`18` 单独成一个文件，是因为它补的是**数据**不是结构：库里 `core.health_condition` 原本只有
`hypertension` 一行，后端 `_check_conditions` 会校验提交的 `condition_id` 必须在这张表里，
所以前端保存另外三种病会 400、Agent 建档会 422。这一条不补，RAG 和验收都没问题，但业务一联调就卡住。

三条硬约束：

1. **12 放在 03 之前**。03 是"对当时存在的对象逐个授权"（`GRANT ... ON ALL TABLES IN SCHEMA app` 这类语句），
   所以放在 12 之后，新增的 `v_profile_effective`、`is_condition_map_valid`、重建后的 `search_ingredients`
   才能一次授权到位。顺序颠倒也不是跑不起来（12 里有"diet_app 已存在就补授权"的 DO 块，03 还有
   `ALTER DEFAULT PRIVILEGES` 兜底），但容易出现"某个新对象没人授权"的偶发问题，排查起来费时。
2. **04 用本包这份**。旧版第 7 段查 `app.v_condition_rule_branch_acceptance`，那个视图已被 12 删除，
   旧脚本会直接 `relation does not exist`。
3. **pg_restore 必须 18**。归档版本 1.16，PG17 及更早的工具会报 `unsupported version (1.16)`。

如果只是把已存的 v1.2 库升到 r1，跳过第 1、2 步，直接跑 12、03、18、04。

RAG 向量化是可选步骤，需带 pgvector 的实例（容器就用 `pgvector/pgvector:pg18`，数据卷挂
`/var/lib/postgresql`）；顺序排在 03 之后、04 之后都行，但一定要在 03 之后——`diet_app` 读
`knowledge` 的权限是 03 授的，反了检索函数会报 permission denied。

## 三、这次改了什么（后端需要知道的）

**1. `app.profile.conditions` 定调为 jsonb 对象映射。**
形状固定为 `{"<condition_id>": {"status": "confirmed|suspected|unknown", "<override_key>": <number>}}`。
写入前由 `app.is_condition_map_valid(jsonb)` 校验，库上另加了 CHECK 约束
`profile_conditions_contract_check`（用 `NOT VALID` 方式加入，只约束新写入，历史行不动）。
后端原来的写法如果是 `["HTN"]` 这种数组形状，会被拦（23514），需要改。

**2. 食材检索接口返回列变多。**
`app.search_ingredients(text, int)` 现在 18 个出参（原 12 个），视图 `app.v_ingredient_search` 25 列。
出参顺序：`food_id`、`name`、`aliases`、`category`、`state`、`energy_kcal`、`protein_g`、`fat_g`、
`carbohydrate_g`、`allergens`、`allergen_status`、`purine_level`、`match_type`、`data_quality`、
`source_note`、`iodine_ug`、`sfa_g`、`has_missing_macro`。
新增 5 个字段：`data_quality`、`source_note`、`iodine_ug`、`sfa_g`，以及沿用旧定义的 `has_missing_macro`。
取值口径：`source_note` 先取逐行 `source_row->>'source_note'`，没有则回退 `core.data_source.notes`；
`iodine_ug` 先取 `micro_nutrients->>'iodine_ug'`，没有则回退 `source_row->>'iodine_ug'`；
缺失一律 NULL，不补 0。后端如果按位置取值（`SELECT *` 后取第 n 个），要改成按列名取。

二轮评审补的 R1 就落在这里：视图一直有 `purine_level`，函数漏了，接口契约 API-11 与 v1.1 的
field_expose 都要这一列，现在补上，位置按视图列序放在 `allergen_status` 之后。

**3. `staging` schema 已整层移除。**
4 张 raw 表（以及它们带来的数据副本）不再随库交付。溯源不受影响：`core.ingredient` 与 `core.dish`
都有逐行 `source_row` jsonb，配合 `core.data_source` 与 `audit.import_batch` 足以还原来源。

**4. 虚构测试视图已删。**
`app.v_condition_rule_branch_acceptance`（注释里自己写着"完全虚构"，硬编码 TEST-RULE-BASE /
TEST-RULE-OVERRIDE）已删除。验收改为用真实规则行跑两条分支：confirmed → `no_intake_data`，
suspected → `condition_not_active`。

**5. legacy 方案没删，改打标记。**
3 条 legacy 计划与 1 条迁移报告保留，加了 retention 标记，验收会断言它们仍在（避免"清理"把历史数据清掉）。

**6. 新旧 profile 字段并存，以新为准。**
`sex` / `goal` 保留但只作兜底：视图 `app.v_profile_effective` 优先读新字段（`gender` / `goal_code`），
旧字段有值时通过 `gender_from_legacy` / `goal_code_from_legacy` 两个布尔列标出来源。
`activity_level` / `extras` / `taboos` 补了 COMMENT，标记为 v1.1 只读保留字段。
后端读档案请走这个视图，不要直接读 `app.profile` 的旧列。

**7. 50–64 岁女性铁参考并回一行（R2）。**
原来这一格按月经状态拆成两行（无月经 10、有月经 12），而 `app.match_nutrient_reference` 的过滤条件是
"记录本身没写月经状态 或 请求没给 或 相等"，档案里没采月经状态时两行同时命中，返回
`needs_clarification=true`，等于每次算铁都要追问一次。现在并回一行：`menstrual_status` 置空、
`value` 取 12（有月经那一侧，保守），`source_row` 里留了 `review_decision=R2-merge-50-64-female-iron`
与 `merged_from` 原始两行。18–49 岁女性仍是 18、65 岁以上仍是 10，没有动。

注意：这次改的是库内数据，源文件 `rni_reference.json` 的 `iron` 仍是两行，需要数据岗下次整理时同步，
否则重新灌库会把修订覆盖回去。12 的 R2 块是幂等的，重灌后再跑一次 12 也能改回来。

**8. 02 结构文件与 10/11 的版本关系。**
`02` 是 v1.2 基线（未改动），`10`/`11` 取自执行 12 之后的实际目录（v1.2r1）。
两者的差异全部由 12 引入，逐条对应见 17，所以直接拿 02 跟 10 对表会看到"少了几张表"，
那是 staging 被删、测试视图被删、新列与函数被加上的结果，不是数据不一致。

## 五、数据说明（沿用 v1.2，未改动）

128 种食材、60 道菜、254 条菜式-食材关系、5 类目标结构映射、7 种关键微量营养素。
新增的 30 道家常菜（DISH-031 至 DISH-060）参考国家卫生健康委公开食养指南，按项目食材池与单人份口径标准化；
指南未给油盐量的按估算值处理，营养结果按食材成分与克数计算。
绿豆芽（CN-400）与燕麦片（CN-1274）的过敏原状态仍是"未核查"，这不表示已确认含过敏原，
候选生成时应保留该提示。

数据库负责存储与约束；候选生成、目标计算、意图识别与 Agent 调度仍由后端与规则引擎完成。
