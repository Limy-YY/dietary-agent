# 数据库验收执行说明（QA-04）

> 维护：测试岗 · 马英慧 ｜ 响应数据岗 2026-11-13 日志求助（缺 pg_restore 18 + pgvector 环境）
> 2026-11-15 修订：一键起库补到 v1.2r1（增加 12 整改 / 18 病种 / 14 RAG），并修正两处会导致失败的配置。
> 目标：任何成员本机一条命令起库，复现 v1.2r1 整体验收，与数据岗 `05_数据库整体验收结果.txt` 对齐。

## 一、前置条件

- 已安装 Docker Desktop（Windows：需 WSL2 后端），且引擎已启动。
- 仓库根目录下 `database/` 交付包齐全，先校验完整性：

```bash
cd database
sha256sum -c 09_文件校验值.sha256
```

任何一行 FAIL 都要停下找数据岗重传，不要带伤还原。

- **端口**：compose 默认映射 `5432:5432`。若本机已有后端容器 `diet-agent-pg` 在跑并占用 5432，先 `docker stop diet-agent-pg`，或把 compose 改成 `"5433:5432"`。两者容器名不同（`diet-agent-pg` / `diet-agent-db`），验收全部走 `docker exec`，不受端口影响。

## 二、一键起库（自动还原）

```bash
cd deploy
docker compose up -d
```

首次启动会自动依次执行（见 `db_init/01_restore.sh`，共 6 步）：

1. `CREATE EXTENSION vector`（镜像自带 pgvector，必成功）；
2. `pg_restore` 还原 `database/01_完整数据库备份_diet_agent_v1.2_60道菜.dump`（显式 `-U diet_app`，否则默认以 `postgres` 连接会报 role 不存在）；
3. 应用 `database/12_数据库整改_v1.2_to_v1.2r1.sql` —— **写入 `audit.schema_migration` 的 r1 / r1b 两个标记**，这是 04 验收第 88 / 172 行断言的硬性前提；
4. 应用 `database/18_病种字典补齐_v1.2r1.sql` —— 补齐 diabetes / gout / hyperlipidemia 三行，使 `core.health_condition` 达到 4 行；
5. 应用 `database/14_RAG向量化_v1.2r1.sql` —— 建 `vector(1024)` 列、HNSW 索引与检索函数（失败仅告警，不计入 27 项判定）；
6. 应用 `database/03_应用账号与权限.sql`（放在最后，统一覆盖 12 / 14 新增对象）。

健康检查通过（`docker compose ps` 显示 healthy）即还原完成，日志末尾应见 `[db_init] 完成：v1.2r1 库已就绪`。

**为什么第 3 步要临时禁用触发器**：12 的 P3 段（L357-364）要给 `legacy-v1.1` 的 meal_plan 打保留标记，而 01 dump 里这些方案已是 `fixed` 状态，UPDATE 会被 `trg_guard_meal_plan_update` 拒绝（`ERROR: meal plan N is fixed and read-only`）。数据岗交付的 12 未处理此情形——其 05 验收走的是 02 结构重建库，那里没有 fixed 方案，所以没暴露。`01_restore.sh` 在 12 执行期间 `DISABLE TRIGGER trg_guard_meal_plan_update`，跑完立即 `ENABLE`，三次独立 psql 调用避免 pending trigger events 整体回滚。**未修改 12 交付物，以免破坏 `09_文件校验值.sha256`。**

**重置重来**：`docker compose down -v && docker compose up -d`。
数据卷挂载点已由 `/var/lib/postgresql/data` 改为 `/var/lib/postgresql`——PG18 官方镜像的 `PGDATA` 是 `/var/lib/postgresql/18/docker`，挂在 `data` 子目录时数据实际不落在卷里，`down -v` 清不掉，重置会失效。

## 三、跑整体验收（04 脚本）

```bash
docker exec -it diet-agent-db psql -U diet_app -d diet_agent -f /delivery/04_数据库整体验收.sql \
  | tee 04_验收_本机结果.txt
```

判定标准：

- 脚本以 `\set ON_ERROR_STOP on` 运行，**任何断言失败会中途退出、退出码非 0**；
- 逐段比对输出与 `database/05_数据库整体验收结果.txt`：表结构断言、基础数据计数（128 食材 / 60 菜 / 254 菜式食材关系 / 5 目标映射 / 7 关键微量）、计划流程、60 道菜明细逐行一致；
- 全部一致 → 记 **27/27 通过**；有差异 → 截图差异行报数据岗，不要自行改库。

**注意**：`05` 正文是 v1.2r1 的结论与摘录，文件尾部附录 A 是 **v1.2 基线**的旧版 04 输出（其汇总表只有 7 项，无 r1/r1b 标记与 staging 断言），比对时不要拿附录 A 当基线。r1b 版 04 的汇总表是 **11 项**：

```
dishes 60 / goal_mappings 5 / ingredients 128 / key_micronutrients 7 / legacy_plans_preserved 3
r1_migration 1 / r1b_migration 1 / schema_migration 1
staging_schema_removed true / test_view_removed true / test_rows_after_rollback 3
```

## 四、手工路径（不用 compose 时）

```bash
createdb -U diet_app diet_agent
pg_restore --no-owner --no-privileges -U diet_app -d diet_agent database/01_完整数据库备份_diet_agent_v1.2_60道菜.dump
psql -U diet_app -d diet_agent -f database/12_数据库整改_v1.2_to_v1.2r1.sql
psql -U diet_app -d diet_agent -f database/18_病种字典补齐_v1.2r1.sql
psql -U diet_app -d diet_agent -f database/14_RAG向量化_v1.2r1.sql
psql -U diet_app -d diet_agent -f database/03_应用账号与权限.sql
psql -U diet_app -d diet_agent -f database/04_数据库整体验收.sql
```

要求 PostgreSQL 18 或兼容版本；`pg_restore` 版本需 ≥ dump 生成版本，否则报「unsupported version in file」。
手工路径跑 12 时同样会撞到 `trg_guard_meal_plan_update`，需先执行：
`ALTER TABLE app.meal_plan DISABLE TRIGGER trg_guard_meal_plan_update;`，跑完再 `ENABLE TRIGGER`（分两次独立事务执行）。

## 五、与后端联调

- compose 暴露 `5432`，连接串：`postgresql://diet_app:diet_app_dev@localhost:5432/diet_agent`；
- 该账号密码**仅限本地验收**，正式部署前必须更换并走 03 脚本的权限组；
- 后端 `backend/` 的数据库配置指向本容器即可，无需各自装 PG。

## 六、已知边界

- `pgvector` 扩展：本镜像自带，14 脚本可正常执行；RAG 检索结构属于 v1.2r1 交付内容，但不计入 04 的 27 项判定；
- 数据岗待补数据（铁源 `rni_reference.json` 两行、纤维 60/60、钙 43/60）到位后会重灌，届时基线计数以新交付说明为准，本说明同步更新；
- 绿豆芽、燕麦片过敏原为「未核查」，是数据状态不是缺陷，验收时不得改为已核查。
